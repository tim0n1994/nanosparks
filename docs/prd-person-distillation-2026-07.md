实测（`prisma.turn` 全表）：


逐集看：

| 集 | 时长 | 段数 | 未归属 | Participant 行 |
|---|---|---|---|---|
| 谢赛宁 7 小时马拉松访谈 | — | 5734 | **100%** | 谢在宁(guest) / 小俊(host) 都在，各 0 段 |

**根因是一个自举死锁，而且代码注释描述的行为和代码本身不一致：**

```
diarize.ts:46       pyannote 跑出真实说话人时间线 result.segments
diarize.ts:63-70    注释：「Store diarization segments as a JSON field」
                            「The normalize_turns job will read this」
                    实际写入：retentionPolicy = "diarized:2"   ← 只有一个计数
                    → segments 被丢弃，从未持久化

normalize-turns.ts:56-62
                    需要 segments，于是「从已经有 participant 的 turn 反推」：
                      turns.filter(t => t.participant?.speakerLabel)
                    新一集里没有任何 turn 有 participant → 空数组

normalize-turns.ts:104
                    participantByLabel.get(undefined) → null
                    → 整集所有 turn 的 participantId 都是 null
```

归属需要先有归属。第一次跑必然全空，而且不会报错——**它安静地成功了**。

柯丽一鸣那集的 8.8% 来自 `analyze.ts:887` 的 LLM 兜底（无 diarization 时单次 LLM 打标），只覆盖一小部分。

**这对整个蒸馏命题意味着什么**：PRD 原本说「L1 归属层缺的是跨集链接」。实际是
**单集之内就没建立**。在补 `Participant → Entity` 之前，得先让 `Turn → Participant` 真的有值。
你要求的「精确还原说话人对应的说话内容」——目前的实际达成率是 **1.6%**。

设计见 §5（AI 驱动流水线）。

### 0.1 原结论：蒸馏对象错人

**你的直觉是对的，而且比你说的更强。但现在这套系统蒸馏的不是那个人——是别人谈论他时说的话。**

现有 `PersonProfile` 的风格卡，取样 SQL 是这一句：

```sql
-- src/lib/person/profile-builder.ts:88-91
SELECT t.text FROM "Turn" t
WHERE t.text ILIKE '%' || $1 || '%'    -- $1 = 这个人的名字
ORDER BY t."createdAt" DESC LIMIT 12
```

它捞的是**「文本里出现了这个人名字」的段落**。在一场访谈里，说出嘉宾名字的绝大多数是主持人。所以：

> 柯丽一鸣的「语言风格卡」，是从张小珺说他名字的那些句子里蒸馏出来的。

代码注释自己承认了这件事：

```ts
// src/lib/person/profile-builder.ts:86-87
// exact speaker attribution (V1) would be tighter but
// requires participantId↔entity linking not yet built.
```

这不是一个 bug，是**整条链路缺了中间那一环**。补上它，你描述的 infra 才成立。

## 1. 现状诊断：链路在哪里断的

### 1.1 断点：`Participant` 没有跨集身份

```prisma
// prisma/schema.prisma:222-237
model Participant {
  id             String
  conversationId String        // ← 只属于一集
  name           String
  speakerLabel   String?       // "speaker_0"
  ...
  // 没有 entityId
}
```

`Participant` 是**一集之内**的说话人。同一个人在 A 集是 `Participant#1`，在 B 集是 `Participant#2`，两行之间**没有任何关联**。

而 `Entity`（真实人物）通过 `EntityMention` 关联到 conversation —— 但 `EntityMention` 记录的是**提及**，不是**发言**：

```prisma
// prisma/schema.prisma:363-378
model EntityMention {
  entityId       String
  conversationId String
  turnId         String?      // 这个 turn 里"提到了"该实体
  surfaceForm    String
}
```

于是形成了这个错位：

```
真实的人 (Entity) ──EntityMention──> 提到他的段落        ← 现在用的是这条
                        ✗
                   （缺失的链路）
                        ✗
一集里的说话人 (Participant) ──> 他自己说的段落 (Turn)   ← 应该用的是这条
```

### 1.2 连带损伤

| 位置 | 症状 | 后果 |
|---|---|---|
| `profile-builder.ts:88` | 风格卡取样错人 | 蒸馏对象错误 |
| `profile-builder.ts:63-78` | `stats` 从 `EntityMention` 统计 | `conversationCount` 数的是「被提到几集」不是「说了几集」 |
| `profile-builder.ts:23,109` | `chatEnabled` 门槛用上面那个错的计数 | **安全阀门量错了量** |
| `profile-builder.ts:131-148` | `coAppears` 是「共同被提及」 | 不是「同台对谈」 |
| `schema.prisma:436` | `SpeakerVoiceprint` 表存在，业务代码引用数 **0** | 最强的身份信号完全没接 |

### 1.3 已有的好底子（不要推翻）

- `ThoughtUnit.participantId`（`schema.prisma:268`）——**这是对的**，命题已经归属到说话人了，只是止步于单集

## 2. 把你的想法推到底：蒸馏出来的到底是什么

### 2.1 播客作为「个体表征」为什么特别好

你说「播客是人与人的思想深度沟通」。我把它拆成五个可利用的技术性质：

| 性质 | 为什么其他文本没有 | 可提取的信号 |
|---|---|---|
| **有对手** | 文章是打磨过的终稿；对谈里有人追问 | 让步 / 闪避 / 改口 —— 压力下的真实边界 |
| **长时程** | 推文 280 字，播客 3 小时 | 斯坦福证明 2 小时访谈够复现 85% 的行为 |
| **重复出场** | 一本书是一个时间点 | 同一个人的**时间序列** |
| **同题重问** | —— | 不同年份回答同一个问题 → 观念漂移可直接测量 |
| **口语未经洗练** | 书面语把思维痕迹洗掉了 | 类比选择、自我修正、口头禅 —— 最个人化的部分 |

第 3、4 条是核心。**单次访谈只能得到一个快照；播客给的是同一个心智的纵切面。** 这是这个产品真正独有的东西，Delphi 那类自建克隆做不到（它们只有当下的你）。

### 2.2 两个蒸馏对象：嘉宾蒸馏「想法」，主持人蒸馏「问法」

**这是本 PRD 最重要的一次分叉。** 同一条流水线，两个截然不同的目标函数：

| | 嘉宾（guest） | 主持人（host） |
|---|---|---|
| 蒸馏什么 | **观点**：他相信什么、凭什么、怎么变的 | **提问策略**：他怎么开场、追到什么程度、何时反驳、何时放过 |
| 核心信号 | `type=claim` + `stance=assert` | `type=question` + 追问链结构 |
| 观点怎么处理 | 就是产物本身 | **必须排除** —— 主持人复述嘉宾观点不代表他的立场 |
| 产物用途 | 可溯源观点档案 | **可执行的访谈者**（见 §4） |

**为什么主持人的档案质量天然最高**：他在自己每一集里都说话，语料量是任何嘉宾的 N 倍，且风格稳定（同一个人、同一个节目定位、同一套开场习惯）。嘉宾要攒够 3 集才有像样的档案，主持人第一天就够。

**但主持人档案有个特有陷阱**：主持人说的话里，大量是**复述、引导、扮演反方**。
- 「所以你的意思是 AGI 五年内到？」——这不是他的观点，是澄清式追问
- 「有人会说这太乐观了」——这是他在扮演反方，不是他相信这个
- 「对，我也这么觉得」——这才可能是他的立场

因此**主持人的 `modality` 抽取必须比嘉宾更严格**（§7.2）。若把主持人的引导性提问当成他的主张，档案会完全失真——而这恰恰是最容易犯的错，因为主持人的话最多。

**主持人指纹卡的字段**（与嘉宾指纹卡不同的一套）：

```
开场模式      他怎么起头（背景铺陈型 / 直球型 / 个人化型）
追问深度      平均追问链长度；何时停止
追问触发器    什么样的回答会让他追问（模糊 / 数字 / 反直觉 / 矛盾）
反驳策略      直接质疑 / 引第三方 / 举反例 / 沉默施压
话题弧线      一集 3 小时里议题如何推进、何时收
过渡话术      他惯用的转场句式
放行信号      他什么时候满意了、怎么表示
```

### 2.3 蒸馏物的四层定义

不要把「蒸馏」理解成「摘要」。摘要是有损压缩，蒸馏是**结构化重组**。

```
L3 结构层  思想指纹    先验 / 论证习惯 / 引用谱系 / 变化史
              ↑ 跨集聚合 + 时间建模
L2 命题层  可溯源主张   他断言了什么，什么立场，多确信，凭什么
              ↑ 单集抽取 + 跨集归并
L1 语料层  归属发言     他自己说的每一段（不是别人说他的）
              ↑ 身份解析 ← 现在断在这里
L0 身份层  跨集同一人   声纹 + 元数据 + 文本自指
```

**L3「思想指纹卡」的字段设计**（每一项都必须带引文，无引文不出现）：

```
核心主张      按 复现次数 × 置信度 排序的 canonical claims
立场光谱      每个话题上他的位置 + 漂移箭头
论证风格      证据类型分布（亲历 / 数据 / 引权威 / 类比 / 无）
              对冲率（「我觉得可能」占比）、让步率
引用谱系      他反复引用谁 —— 智识来源
类比词汇      他惯用的比喻 —— 高度个人化，几乎是签名
变化史        立场翻转的命题，两侧引文并列
回避区        主持人反复问、他反复绕开的话题
```

最后一项「回避区」信息量极高，也**最危险**——放在 §11 讲。

### 2.4 北极星修正：不是「人物档案产品」，是「个体蒸馏 infra」

> 我原本问了个问题：「主持人指纹用谁的？这决定产品是主持人风格市场还是单一自有访谈者。」
> 你说没太理解——**因为这个问题问偏了**。我在问商业形态，你关心的是这件事的本质。
> 你的原话：
>
> > 通过深度对谈蒸馏越来越多的受访者，一个人参加越来越多的播客节目就可以更好地蒸馏他自己。
> > 以后这套以对谈内容为主再补充其他数据源的 infra 就能成为蒸馏个人的最佳实践。
> > 带思考的交谈带着我们每个人的语言风格、思考风格，融合了我们的心理状态、动机等等理念世界，
> > 能更客观地表征每个具体的人。
>
> 这把重心整体上移了一层。AI 主持人（§3）不是产品目的，**是手段**——是为了制造更多
> 深度对谈，来蒸馏更多的人。下面按这个定位重写。

**修正后的定位**：

```
不是：一个能查某人说过什么的网站
而是：以对谈为主源、可融合其他数据源的「意识与思维风格蒸馏 infra」
```

#### 为什么「观点」不够，必须做到「思考风格」

观点会变，思考风格几乎不变。**后者才是更稳定、更客观的个体表征**——这正是你说的
「更客观地表征每个具体的人」的技术含义。而且它可以从同一批转写里抽，不需要新数据源：

| 维度 | 可观测信号（都在转写里） | 为什么个人 |
|---|---|---|
| **推理链长度** | 结论前铺垫几步：一步到位 vs 层层推演 | 认知风格，几乎不随话题变 |
| **抽象层级偏好** | 从第一性原理往下推 vs 从具体案例往上归纳 | 训练背景的指纹 |
| **不确定性处理** | 给区间 / 给点估计 / 拒绝估计 | 与专业训练强相关 |
| **反例响应** | 被举反例后：修正立场 / 辩护 / 忽略 | 智识诚实度，极稳定 |
| **时间尺度** | 习惯用什么跨度论证（季度 / 十年 / 百年） | 世界观的直接投影 |
| **归因倾向** | 把结果归于结构 / 个人能动性 / 运气 | 深层信念 |
| **类比来源域** | 从物理 / 生物 / 军事 / 商业哪里取喻 | 知识来源的签名 |
| **切换成本** | 换话题时是否带着上个话题的框架 | 思维惯性 |

#### 心理状态与动机——能做，但要节制

这一层最有价值也最容易越界。可操作化的只取**行为可观测**的，不做心理诊断：

| 维度 | 信号 | 明确不做 |
|---|---|---|
| **驱动力** | 他**主动**带回的主题（不是被问的）——反复自发回到什么 | 不推断"他为什么在乎" |
| **情绪激活点** | 语速 / 音量 / 打断率在什么话题上升高 ← **需要音频** | 不标注情绪类别 |
| **自我叙事** | 讲自己的故事时用什么因果结构 | 不评价真伪 |
| **价值排序** | 两难场景下他选哪边（从对谈里的取舍抽） | 不做道德评判 |
| **反对对象** | 他反对什么——比支持什么更能定位一个人 | 不推断敌意 |

「情绪激活点」这一项引出了下一节：**第一个"其他数据源"其实就在手里。**

#### 多源融合架构：分层而非混合

```
        ┌──────────────────────────────────────────┐
主源    │ 播客对谈    压力下的思维、让步、改口      │  权重最高
        │             ← 这是别处拿不到的            │
        ├──────────────────────────────────────────┤
已有    │ 音频副语言  语速/停顿/音量/打断           │  情绪激活点
        │             ← 我们已经有音频，只是没用    │  唯一来源
        ├──────────────────────────────────────────┤
可加    │ 公开写作    打磨后的结论、完整论证        │  补观点广度
        │ 演讲/视频   面向大众的表达                │  不补思考风格
        │ 代码/作品   对技术人：实际取舍            │  行为证据
        └──────────────────────────────────────────┘
```

**关键设计：不能把多源简单合并成一个语料池。** 因为：

- 对谈捕捉的是**压力下的思维**；写作捕捉的是**打磨后的结论**
- 同一个人，写作里的对冲率会显著低于对谈——因为写作可以反复修改
- 若混合计算「对冲率」，得到的数字既不是他说话的样子，也不是他写作的样子

**所以每个指纹字段必须声明它的合法来源**：

```
思考风格 / 对冲率 / 让步率     ← 仅对谈（写作会污染）
情绪激活点                      ← 仅音频
核心主张 / 立场光谱             ← 对谈 + 写作（可合并，标注来源）
引用谱系                        ← 全部来源（越多越准）
类比词汇                        ← 对谈优先，写作次之
```

`PersonFingerprint` 因此要为每个字段带 `sourceTypes[]`——这不是元数据洁癖，
是防止「用写作数据算出的对冲率」冒充「这个人说话的样子」。

### 2.5 什么是「蒸馏做深了」的判据

一句话：**能预测这个人还没说过的话。**

这是可证伪的，而且可以直接跑（§10 详述）：留出他最新一集，用之前所有集蒸馏出的指纹去预测他在这集里对若干议题的立场，和真实转写比对。

## 3. AI 主持人：飞轮闭环

> 这一节来自你的第 1 条回复。它把系统从「消费已有播客」变成「生产新播客」，是整份 PRD 里商业价值最高的一段。

### 3.1 闭环是怎么合上的

```
   真实播客 ──转写──► 主持人蒸馏 ──► 可执行访谈者
       ▲                                    │
       │                                    │ 与真人对谈
       │                                    ▼
       └────── 新的对谈语料 ◄──── 生成的节目
```

**关键点：这个环有正反馈。** 生成的节目本身是新语料，既能继续喂主持人指纹（让它更像那个主持人），也能喂**受访者**的指纹（一个原本没上过播客的人，现在有语料了）。

而且这不是空想——**斯坦福那篇论文正是这么做的**：1052 个人的 2 小时访谈，是由一个 **AI 访谈者**按标准化协议 + 动态追问完成的，因为「1000 场访谈超出单个研究生的时间」。他们证明了 AI 访谈者能采出足够复现本人行为的信息量。我们比他们多一样东西：**我们的 AI 访谈者不是通用协议，是某个真实优秀主持人的蒸馏。**

### 3.2 访谈者 = 三个组件，不是一个 prompt

把主持人指纹直接塞进 system prompt 会得到一个"语气像但不会问"的东西。真正的访谈者需要：

| 组件 | 职责 | 来自指纹的哪一部分 |
|---|---|---|
| **弧线规划器** | 一场访谈的议题顺序与时间预算 | 话题弧线 |
| **追问引擎** | 判断当前回答是否"过关"，不过关就追 | 追问触发器 + 追问深度 |
| **风格层** | 措辞、过渡、语气 | 开场模式 / 过渡话术 |

**追问引擎是核心，也是最容易做砸的地方。** 它需要一个明确的「回答质量判据」：

```
回答被判为"需要追问"，当且仅当满足任一：
  · 含模糊量词而无具体数字（"很多"/"不少"/"挺快"）
  · 给了结论但没给依据
  · 与该受访者此前语料中的表述冲突   ← 这里用到了受访者的指纹
  · 回避了问题的核心（答非所问检测）
  · 出现了值得展开的新实体/概念
追问链长度上限 = 该主持人指纹的 P75 追问深度（不是无限追）
```

第 3 条是这套系统独有的能力：**AI 主持人能问出「你 2021 年说过 X，现在为什么改了」**——因为它手上有受访者的双时态命题库（§7.3）。人类主持人做不到这个，除非他事先做了几十小时功课。**这是产品真正的差异化，不是"AI 能对话"这种人人都有的东西。**

### 3.3 产品形态

| 形态 | 说明 | 优先级 |
|---|---|---|
| **AI 采访我** | 用户选一个主持人指纹，被访 30–60 分钟，产出一集可读文稿 | P0，最小可验证 |
| **预演** | 真人主持人在录制前，先让 AI 版嘉宾陪练，看哪些问题会被挡回来 | P1，对创作者价值高 |
| **补问** | 已有一集里主持人漏问的，AI 事后补一轮 | P2 |

### 3.4 回灌策略（已拍板）

> 你的第 1 条回复：**受访者的真人发言回灌，AI 主持人的话不回灌。**

```
生成的一集里
  受访者说的话  ──►  回灌语料库  ✓  这是真人产出的新语料，是飞轮的燃料
  AI 主持人的话 ──►  不回灌      ✗  回灌会让主持人指纹拟合自己的输出 → 模型坍缩
```

实现上要求：生成节目的每一段在入库时带 `speakerKind: human | ai`，
蒸馏管线只消费 `human`。这个字段必须在**写入时**就打上，不能事后靠猜——
一旦混进去，之后无法区分。

### 3.5 与嘉宾蒸馏的依赖关系

AI 主持人**依赖**受访者指纹才能发挥全部能力（追问引擎的第 3 条）。所以路线上它排在嘉宾蒸馏之后，但**基础版（弧线 + 风格 + 前两条追问触发器）不依赖**，可以早做。

### 3.6 必须标注

生成的节目、AI 主持人的每一句话，都要**显式标明是 AI**。这一条我按产品质量要求保留，与法律无关——用户如果分不清对面是不是真人，这个产品的信任基础就没了。技术上沿用 §11 的双标识方案。

### 4.1 一个必须点破的差异

Delphi / Character.AI 是**本人同意的自我克隆**。我们做的是**从第三方公开发言中析出的人物档案**。

这不是程度差别，是性质差别。它决定了：**主产品不能是「和某某聊天」，只能是「某某说过什么、怎么变的、凭什么」**。交互问答是受控的次级功能，不是主线。

> 是**接线断了**（§0.0）和**几个模块是死代码**。下面按"已有 / 断了 / 缺"三分来设计。

`asr-eval.ts` 死掉是真问题：**你要求"精确且性能优秀"，但没有任何东西在测量精确度。**

### 5.2 目标链路：五个 AI 决策点

```
用户输入（链接/播客名/主页/RSS…任意形式）
        │
   ① [Agent] 入口解析 ──────────► 单集 or 多集清单
        │                          工具调用循环，失败自主换策略
        ▼
   ② 音频获取 + ASR ────────────► 原始转写 + 词级时间戳
        │
   ③ [AI] 说话人归属 ───────────► Turn.participantId  ← 现在 1.6%，目标 ≥95%
        │                          diarization ⊕ 对话逻辑 ⊕ LLM 裁决
        ▼
   ④ [LLM] 校正 ────────────────► 专名/同音/断句，不改语义
        │                          术语表引导 + 低置信优先
        ▼
   ⑤ [AI] 质量门 ───────────────► 不达标不进蒸馏层
                                   可量化、可拒绝、可重跑
```

### 5.3 ① Agentic 入口解析

现有 `resolvers/` 已有 10+ 个 provider 和 `discover.ts`。要补的是**决策层**：

```
输入 → 分类（URL / 节目名 / 主页 / RSS / 频道）
     → 选策略 → 执行 → 失败？→ 换策略（不是报错）

策略降级链示例（Spotify）：
  1. Spotify 页面 HTML 抽 show name        → 失败
  2. Spotify oEmbed                        → 超时（实测 §上一轮）
  3. 用已抽到的 show name 查 iTunes RSS    → 成功 ✓
  4. 都失败 → 让用户输入节目名（已实现）
```

这一层的关键设计是**「失败是信号不是终点」**：每次降级都记录 `kind`，
既用于给用户可执行的下一步（上一轮已落地 `platform_unreachable`），
也用于给 Agent 下次同平台的策略排序。

### 5.4 ③ 说话人归属 —— 本节的核心

这是 §0.0 那个 98.4% 要修的地方。**三源仲裁，而不是单一来源**：

```
源 A  diarization 时间线（pyannote）
      → 必须真正持久化！现在被丢成了一个计数
      → 新增 DiarizationSegment 表（见 §8）

源 B  对话逻辑（纯规则，零成本，出奇地强）
      → 问句之后大概率换人
      → "对/嗯/是的" 这类回应词归属于"上一句的听者"
      → 长独白中间的短插话通常是另一个人
      → 主持人开场/收尾的位置先验

源 C  LLM 裁决（只在 A 与 B 冲突或缺失时调用）
      → 给它：前后各 5 段文本 + 已知说话人名单 + 角色
      → 让它只输出 speaker 标签，不许改文本

融合：
  A、B 一致            → 直接采纳，置信 0.95
  A、B 冲突            → 调 C 仲裁，置信取 C 的自评
  A 缺失（无 diarization）→ B 打底 + C 兜底
  三源都拿不准          → participantId = null，但**必须记录原因**
```

**最后一条是设计要点**：现在的 null 是静默的，分不清"没跑"和"跑了但不确定"。
增加 `Turn.attributionMethod`（`diarization | dialogue | llm | none`）
和 `Turn.attributionConfidence`，让 1.6% 这种数字**在仪表盘上自己暴露出来**，
而不是靠人去查库才发现。

**性能**（你强调的）：源 B 是纯字符串规则，7395 段跑完 <100ms。源 C 只在冲突时调用，
按实测冲突率估计约 10–15% 的段落，一集 3 小时约 150 次调用，可批量（每次 20 段）
→ 约 8 次 LLM 调用/集，成本可忽略。**不要对每一段都调 LLM，那是 100 倍成本换 5% 收益。**

### 5.5 ④ LLM 校正（已有，需加固）

`correction-pass.ts` 的约束设计是对的（不改语义、不改时间戳、只改文本）。要补三点：

1. **术语表要自动生长，不能只靠手工**
   现在 `hotwords.ts` 从 `Setting` 读，是人工维护的。应该：
   每集抽出的高置信实体（人名/公司/技术名）→ 回写节目级术语表 → 下一集校正更准。
   **这就是你说的 infra 复利，在最底层的体现。**

2. **优先校正低置信段**
   ASR 通常给 token 置信度。全量校正是浪费；按置信度排序，只校正后 20%。

3. **校正必须可回溯**
   保留原始 ASR 文本，校正作为一层 overlay（`Turn.text` 存校正后，
   新增 `Turn.rawText` 存原始）。校正器自己也会出错，没有原文就无法审计。

### 5.6 ⑤ 质量门 —— 让「精确」可测量

`asr-eval.ts` 已存在但零引用。接上它，并定义**进入蒸馏层的准入条件**：

| 指标 | 怎么算 | 阈值 | 不达标怎么办 |
|---|---|---|---|
| 转写覆盖率 | `max(turn.endMs) / durationMs` | ≥98% | 重跑 ASR |
| 说话人归属率 | `1 - null率` | ≥95% | 重跑归属，仍不达标则**只进 T0，不进蒸馏** |
| 归属置信中位数 | `median(attributionConfidence)` | ≥0.8 | 同上 |
| 校正改动率 | 被改字数 / 总字数 | ≤8% | 超过说明 ASR 质量差或校正器跑飞，人工看 |

**「不达标则不进蒸馏层」是这套设计里最重要的一条纪律。** 一集归属率 60% 的语料
喂进指纹层，产出的不是"稍差的画像"，是"看起来很像但错得理直气壮的画像"——
这比没有画像危险得多。

### 5.7 落地顺序

| 步 | 做什么 | 判据 |
|---|---|---|
| **S1** | 新增 `DiarizationSegment` 表；`diarize.ts` 真正持久化 segments | 表里有数据 |
| **S2** | 重写 `normalize-turns` 的归属逻辑，解开自举死锁，接入源 A+B | 归属率 从 1.6% → ≥85% |

### 6.1 复利飞轮（你说的 infra 就是这个）

具体机制，不是空话：

## 7. 关键算法设计

### 7.1 身份解析（L0）—— 三信号融合

**不要只用声纹。** 声纹的失败模式很具体：

- 同一人换麦克风 / 不同平台转码 → embedding 漂移
- 跨年份（声音会变）
- 远场 / 电话连线嘉宾
- 中文播客大量存在的「同一集里多人重叠说话」

**三路信号**：

| 信号 | 来源 | 精度 | 召回 | 成本 |
|---|---|---|---|---|
| **声纹** | WeSpeaker/pyannote embedding，段级均值 | 中高 | 高 | 需过一遍音频 |
| **元数据** | RSS `<itunes:author>`、标题「对谈X」、show notes | **很高** | 低（常缺失） | 几乎为零 |
| **文本自指** | 「我是X」/ 主持人「欢迎X」/「我在Y公司」 | 高 | 中 | 一次 LLM |

**融合策略**（分数级融合 + 显式不确定带）：

```
score = w_v · cos(voiceprint) + w_m · meta_match + w_t · text_match

score ≥ 0.85            → 自动关联
0.60 ≤ score < 0.85     → 进人工确认队列   ← 这一带是产品质量的关键
score < 0.60            → 新建 Entity
```

中间带**必须存在且必须有 UI**。实体消歧文献（Splink / Zingg 这一路）的共识就是：高精度阻塞 + 成对打分 + 聚类 + **不确定带人工复核**。没有这一环的系统一定会脏。

**错误合并是最贵的错误**——它会毒化整个人物档案，且难以察觉。因此：

- `SpeakerIdentity` 是**关联表**，不是把 `entityId` 塞进 `Participant`
- 合并/拆分是一等操作，带审计轨迹
- 永不破坏性合并：拆开只需删关联行

```prisma
/// L0：一集里的说话人 ↔ 跨集真实人物。关联表而非外键，
/// 因为错误合并必须能无损回滚。
model SpeakerIdentity {
  id            String   @id @default(cuid())
  participantId String   @unique
  participant   Participant @relation(fields: [participantId], references: [id], onDelete: Cascade)
  entityId      String
  entity        Entity   @relation(fields: [entityId], references: [id], onDelete: Cascade)
  confidence    Float
  method        String   // voiceprint | metadata | text | fused | manual
  evidenceJson  Json     // { voiceCos, metaHit, textQuote, reviewerId }
  reviewedBy    String?  // 人工确认者
  reviewedAt    DateTime?
  createdAt     DateTime @default(now())

  @@index([entityId])
  @@index([confidence])
}
```

### 7.2 命题抽取（L2）

现有 `ThoughtUnit` 有 `type` 和 `stance`，需要补三个字段才够支撑「变化检测」：

```prisma
model ThoughtUnit {
  // ...现有字段
  modality    String?  // asserted | hedged | hypothetical | quoted | joking
  evidenceType String? // experience | data | authority | analogy | none
  polarity    Float?   // -1..1，对命题的支持度
}
```

**`modality` 是防止诽谤的关键字段。** 「我觉得可能 AGI 五年内到」和「AGI 五年内一定到」，以及**引用别人的话**「有人说 AGI 五年内到」，在朴素抽取里会被压成同一条命题。一旦压平，「他改口了」的判断就会是错的。

### 7.3 变化检测 —— 最危险的功能，单独设计

**朴素做法（会出事）**：找到 2021 年的命题 P 和 2024 年的 ¬P，输出「他改变了立场」。

**为什么会出事**：矛盾 ≠ 观念改变。可能是
- 语境不同（在讨论不同对象）
- 假设性陈述（「如果……那我会说」）
- 引用他人观点
- 反讽
- 转写错误 / 归属错误（L0 错了这里就全错）

**设计**：

1. 只在 `modality = asserted` 的命题之间比较
2. 要求两侧都有 `EvidenceSpan`（可跳回原音频）
3. 命题需先归一到同一 `CanonicalClaim`，且要求主题语境相似度阈值
4. **系统不下断言**。UI 呈现是：

   > **同一议题，不同时间**
   > 2021-03 ——「……」 ▶ 听原声
   > 2024-08 ——「……」 ▶ 听原声

   而不是「他改变了看法」。让读者自己判断。这既更准确，也是唯一安全的呈现方式。
5. 置信度低于阈值不展示，宁可漏报

**双时态模型**（借 Zep/Graphiti）：

```prisma
model PersonClaim {
  id           String   @id @default(cuid())
  entityId     String                    // 谁说的
  canonicalId  String?                   // 归并到哪个 CanonicalClaim
  text         String
  modality     String
  polarity     Float

  assertedAt   DateTime                  // valid time：他何时说的（用单集发布日）
  ingestedAt   DateTime @default(now())  // system time：我们何时知道的
  supersededById String?                 // 被哪条后续陈述取代
  supersededAt   DateTime?               // 失效而非删除

  thoughtUnitId String                   // 溯源
  @@index([entityId, assertedAt])
  @@index([canonicalId])
}
```

「失效而非删除」很重要：2021 年那句话**当时是真的说了**，它永远不该从档案里消失，只是不再代表当下立场。

### 7.4 统一中文语义层：全中文约束下的风格保全

> 你的第 4 条回复：**不管中文还是英文播客，整个 infra 都基于中文语义，国外播客
> 也必须翻译成中文来做内容整理和蒸馏。** 我之前提的「风格走原文、语义走译文」
> 双轨方案与此冲突，按你的决定改掉。下面是在**全中文**这个硬约束下的最优解。

**先说清代价，再说对策。** 直译会把 L3 里最个人化的两个字段抹平：

| 原文 | 通用翻译 | 丢了什么 |
|---|---|---|
| "it's turtles all the way down" | 「一层套一层」 | 一个有出处的典故，选它本身是信号 |
| "skating to where the puck is going" | 「提前布局」 | 冰球隐喻 → 商业套话，个人色彩归零 |
| 反复的 "look," / "right?" | 通常被丢弃 | 口头禅整体消失 |
| "I'd argue" vs "I think maybe" | 都成「我觉得」 | 确信度梯度被压平 → 对冲率失真 |

不处理的话，所有英文嘉宾的「类比词汇」会长得一模一样——**那是翻译模型的签名，不是他们的**。

#### 对策：蒸馏用翻译 ≠ 阅读用翻译

现有 `translation.ts` 服务的是**阅读**：通顺、地道、符合中文表达习惯。
蒸馏需要的是**另一种翻译**：宁可生硬，也要保住风格标记。两者是不同的 prompt，
产出两份译文，各司其职。

```
翻译用途          目标            处理隐喻            处理对冲词
─────────────────────────────────────────────────────────────
阅读版（已有）    通顺地道        意译成中文习惯用法   统一成「我觉得」
蒸馏版（新增）    保真            直译 + 括注来源域    保留强度分级
```

**蒸馏版翻译的具体约束**（写进 prompt）：

```
1. 隐喻直译，不替换成中文对应习语
   "skating to where the puck is going"
   → 「滑向冰球将要到达的位置」〔冰球〕      ← 括注来源域，供类比词汇统计
2. 对冲词按强度分级映射，不合并
   I'm certain / I'd argue / I think / maybe / sort of
   → 我确信 / 我认为 / 我觉得 / 也许 / 有点        ← 五级，不塌缩成一级
3. 口头禅保留并标记
   反复出现的 "look," / "right?" → 〔口头禅:look〕
4. 自我修正、重复、结巴保留
   阅读版会清掉，蒸馏版必须留 —— 它们是思维痕迹
```

这样「全中文语义层」的约束保住了，风格信号也不至于全丢。**代价是每集多一次翻译调用**
（仅对非中文集），成本可接受。

#### 仍然存在的残差，需要承认

即使按上面做，**译文的风格保真度仍低于原文**。所以：

- 英文集的风格类字段（类比词汇 / 口头禅 / 对冲率）标注 `sourceQuality: translated`
- §10 的评测里，**中文集与英文集分开算指标**，不要混在一个数上
- 优先用中文播客验证 L3 的设计是否成立；英文集作为覆盖度补充

**纯中文播客不受任何影响**——原文即分析文本，风格信号完整。

## 10. 评测体系

不做评测的蒸馏系统等于没做。四层各有指标：

| 层 | 指标 | 方法 | 目标 |
|---|---|---|---|
| **L0 身份** | 合并 precision / recall | 人工标注 200 对 participant，算 P/R | P ≥ 0.98（合并错代价极高，宁可漏） |
| **L1 归属** | 发言归属准确率 | 抽 500 段人工核对说话人 | ≥ 0.95 |
| **L2 命题** | 忠实度 | 人工评「这条命题是否忠实于原话」 | ≥ 0.90 |
| **L2 变化** | **误报率** | 系统标出的立场变化，人工核对真伪 | **≤ 0.05（最危险的指标）** |
| **L3 指纹** | **留出集预测准确率** | 见下 | 北极星 |

### 10.1 北极星：留出集预测

直接移植斯坦福 genagents 的方法论：

1. 取某人的 N 集，留出**最新一集**
2. 用前 N−1 集蒸馏出指纹
3. 从留出集里抽出该集讨论的 K 个议题
4. 让指纹**预测**他在这些议题上的立场
5. 与留出集真实发言比对

这是可跑、可证伪、可持续追踪的。斯坦福在 2h 访谈上做到 85% 行为复现；我们有同一人的多次长对谈，理论上限更高——**如果 L0/L1 是对的**。

**这个指标同时是 L0 的照妖镜**：身份解析错了，预测准确率会立刻塌，比任何单独的归属指标都灵敏。

| 1 | 主持人要不要建档 | **要**，且蒸馏「问法」而非「观点」，进一步用于自动生成节目 | §2.2 + 全新 §3；路线图 P4h / P5a |
| 2 | 跨语言同一人 | 不存在——全部统一到中文语义层分析 | §7.4（并指出翻译对风格字段的副作用与对策） |

### 第二轮已拍板（2026-07-26）

| # | 问题 | 你的决定 | 落到哪里 |
|---|---|---|---|
| 1 | AI 生成内容回灌 | 受访者真人发言回灌，AI 主持人的话不回灌 | §3.4；需 `speakerKind` 字段 |
| 2 | 主持人指纹的商业形态 | **问题问偏了** —— 本质是搭建个体蒸馏 infra，AI 主持人是手段不是目的 | §2.4 北极星整体上移；新增思考风格/心理动机维度 + 多源融合架构 |
| 3 | host/guest 角色判定 | 先把说话人↔内容的精确还原做扎实，全链路 AI 驱动 | **全新 §5**（发现全库归属率仅 1.6%，并给出五个决策点的设计） |

### 仍然未决

1. **`speakerKind` 之外，AI 生成的一集要不要单独隔离成一个 corpus？** 混在真实播客里，
   将来做「跨人对比」时会把 AI 访谈的产物和真实播客的产物放在同一分布里比较。
2. **思考风格的抽取粒度**：按整集算一次，还是按话题段算？后者能发现「他在自己专业领域
   推理链更长，在陌生领域更依赖类比」这类结构，但成本高一个量级。
3. **多源融合的第二源选哪个**：音频副语言（已有数据，唯一能给情绪激活点）
   vs 公开写作（补观点广度但污染风格字段）。我倾向前者，因为数据已在手上。
4. **`asr-eval` 的 ground truth 从哪来**：没有人工标注的转写就无法算 WER。
   是否接受用「LLM 校正改动率」作为代理指标？
