## 0. 先说结论

**你的直觉是对的，而且比你说的更强。但现在这套系统蒸馏的不是那个人——是别人谈论他时说的话。**

现有 `PersonProfile` 的风格卡，取样 SQL 是这一句：

```sql
-- src/lib/person/profile-builder.ts:88-91
SELECT t.text FROM "Turn" t
WHERE t.text ILIKE '%' || $1 || '%'    -- $1 = 这个人的名字
ORDER BY t."createdAt" DESC LIMIT 12
```

它捞的是**「文本里出现了这个人名字」的段落**。在一场访谈里，说出嘉宾名字的绝大多数是主持人。所以：

> 柯丽一鸣的「语言风格卡」，是从张小珺说他名字的那些句子里蒸馏出来的。

代码注释自己承认了这件事：

```ts
// src/lib/person/profile-builder.ts:86-87
// exact speaker attribution (V1) would be tighter but
// requires participantId↔entity linking not yet built.
```

这不是一个 bug，是**整条链路缺了中间那一环**。补上它，你描述的 infra 才成立。

## 1. 现状诊断：链路在哪里断的

### 1.1 断点：`Participant` 没有跨集身份

```prisma
// prisma/schema.prisma:222-237
model Participant {
  id             String
  conversationId String        // ← 只属于一集
  name           String
  speakerLabel   String?       // "speaker_0"
  ...
  // 没有 entityId
}
```

`Participant` 是**一集之内**的说话人。同一个人在 A 集是 `Participant#1`，在 B 集是 `Participant#2`，两行之间**没有任何关联**。

而 `Entity`（真实人物）通过 `EntityMention` 关联到 conversation —— 但 `EntityMention` 记录的是**提及**，不是**发言**：

```prisma
// prisma/schema.prisma:363-378
model EntityMention {
  entityId       String
  conversationId String
  turnId         String?      // 这个 turn 里"提到了"该实体
  surfaceForm    String
}
```

于是形成了这个错位：

```
真实的人 (Entity) ──EntityMention──> 提到他的段落        ← 现在用的是这条
                        ✗
                   （缺失的链路）
                        ✗
一集里的说话人 (Participant) ──> 他自己说的段落 (Turn)   ← 应该用的是这条
```

### 1.2 连带损伤

| 位置 | 症状 | 后果 |
|---|---|---|
| `profile-builder.ts:88` | 风格卡取样错人 | 蒸馏对象错误 |
| `profile-builder.ts:63-78` | `stats` 从 `EntityMention` 统计 | `conversationCount` 数的是「被提到几集」不是「说了几集」 |
| `profile-builder.ts:23,109` | `chatEnabled` 门槛用上面那个错的计数 | **安全阀门量错了量** |
| `profile-builder.ts:131-148` | `coAppears` 是「共同被提及」 | 不是「同台对谈」 |
| `schema.prisma:436` | `SpeakerVoiceprint` 表存在，业务代码引用数 **0** | 最强的身份信号完全没接 |

### 1.3 已有的好底子（不要推翻）

- `ThoughtUnit.participantId`（`schema.prisma:268`）——**这是对的**，命题已经归属到说话人了，只是止步于单集
- `ThoughtUnit.stance`（`:270`）——`assert / oppose / question / concede / neutral`，论证挖掘的骨架已在
- `CanonicalClaim.firstAssertedAt / lastAssertedAt`（`:387-388`）——时间维度的种子已埋
- `entity/resolver.ts` 的三级漏斗（exact → embedding@0.86 → LLM 仲裁）——实体消歧的框架可直接复用到人身上
- `EvidenceSpan`——引文可溯源的基础设施在

**结论：不是重写，是接一条线，然后在这条线上长出四层。**

## 2. 把你的想法推到底：蒸馏出来的到底是什么

### 2.1 播客作为「个体表征」为什么特别好

你说「播客是人与人的思想深度沟通」。我把它拆成五个可利用的技术性质：

| 性质 | 为什么其他文本没有 | 可提取的信号 |
|---|---|---|
| **有对手** | 文章是打磨过的终稿；对谈里有人追问 | 让步 / 闪避 / 改口 —— 压力下的真实边界 |
| **长时程** | 推文 280 字，播客 3 小时 | 斯坦福证明 2 小时访谈够复现 85% 的行为 |
| **重复出场** | 一本书是一个时间点 | 同一个人的**时间序列** |
| **同题重问** | —— | 不同年份回答同一个问题 → 观念漂移可直接测量 |
| **口语未经洗练** | 书面语把思维痕迹洗掉了 | 类比选择、自我修正、口头禅 —— 最个人化的部分 |

第 3、4 条是核心。**单次访谈只能得到一个快照；播客给的是同一个心智的纵切面。** 这是这个产品真正独有的东西，Delphi 那类自建克隆做不到（它们只有当下的你）。

### 2.2 两个蒸馏对象：嘉宾蒸馏「想法」，主持人蒸馏「问法」

**这是本 PRD 最重要的一次分叉。** 同一条流水线，两个截然不同的目标函数：

| | 嘉宾（guest） | 主持人（host） |
|---|---|---|
| 蒸馏什么 | **观点**：他相信什么、凭什么、怎么变的 | **提问策略**：他怎么开场、追到什么程度、何时反驳、何时放过 |
| 核心信号 | `type=claim` + `stance=assert` | `type=question` + 追问链结构 |
| 观点怎么处理 | 就是产物本身 | **必须排除** —— 主持人复述嘉宾观点不代表他的立场 |
| 产物用途 | 可溯源观点档案 | **可执行的访谈者**（见 §4） |

**为什么主持人的档案质量天然最高**：他在自己每一集里都说话，语料量是任何嘉宾的 N 倍，且风格稳定（同一个人、同一个节目定位、同一套开场习惯）。嘉宾要攒够 3 集才有像样的档案，主持人第一天就够。

**但主持人档案有个特有陷阱**：主持人说的话里，大量是**复述、引导、扮演反方**。
- 「所以你的意思是 AGI 五年内到？」——这不是他的观点，是澄清式追问
- 「有人会说这太乐观了」——这是他在扮演反方，不是他相信这个
- 「对，我也这么觉得」——这才可能是他的立场

因此**主持人的 `modality` 抽取必须比嘉宾更严格**（§6.2）。若把主持人的引导性提问当成他的主张，档案会完全失真——而这恰恰是最容易犯的错，因为主持人的话最多。

**主持人指纹卡的字段**（与嘉宾指纹卡不同的一套）：

```
开场模式      他怎么起头（背景铺陈型 / 直球型 / 个人化型）
追问深度      平均追问链长度；何时停止
追问触发器    什么样的回答会让他追问（模糊 / 数字 / 反直觉 / 矛盾）
反驳策略      直接质疑 / 引第三方 / 举反例 / 沉默施压
话题弧线      一集 3 小时里议题如何推进、何时收
过渡话术      他惯用的转场句式
放行信号      他什么时候满意了、怎么表示
```

### 2.3 蒸馏物的四层定义

不要把「蒸馏」理解成「摘要」。摘要是有损压缩，蒸馏是**结构化重组**。

```
L3 结构层  思想指纹    先验 / 论证习惯 / 引用谱系 / 变化史
              ↑ 跨集聚合 + 时间建模
L2 命题层  可溯源主张   他断言了什么，什么立场，多确信，凭什么
              ↑ 单集抽取 + 跨集归并
L1 语料层  归属发言     他自己说的每一段（不是别人说他的）
              ↑ 身份解析 ← 现在断在这里
L0 身份层  跨集同一人   声纹 + 元数据 + 文本自指
```

**L3「思想指纹卡」的字段设计**（每一项都必须带引文，无引文不出现）：

```
核心主张      按 复现次数 × 置信度 排序的 canonical claims
立场光谱      每个话题上他的位置 + 漂移箭头
论证风格      证据类型分布（亲历 / 数据 / 引权威 / 类比 / 无）
              对冲率（「我觉得可能」占比）、让步率
引用谱系      他反复引用谁 —— 智识来源
类比词汇      他惯用的比喻 —— 高度个人化，几乎是签名
变化史        立场翻转的命题，两侧引文并列
回避区        主持人反复问、他反复绕开的话题
```

最后一项「回避区」信息量极高，也**最危险**——放在 §10 讲。

### 2.4 什么是「蒸馏做深了」的判据

一句话：**能预测这个人还没说过的话。**

这是可证伪的，而且可以直接跑（§9 详述）：留出他最新一集，用之前所有集蒸馏出的指纹去预测他在这集里对若干议题的立场，和真实转写比对。

## 3. AI 主持人：飞轮闭环

> 这一节来自你的第 1 条回复。它把系统从「消费已有播客」变成「生产新播客」，是整份 PRD 里商业价值最高的一段。

### 3.1 闭环是怎么合上的

```
   真实播客 ──转写──► 主持人蒸馏 ──► 可执行访谈者
       ▲                                    │
       │                                    │ 与真人对谈
       │                                    ▼
       └────── 新的对谈语料 ◄──── 生成的节目
```

**关键点：这个环有正反馈。** 生成的节目本身是新语料，既能继续喂主持人指纹（让它更像那个主持人），也能喂**受访者**的指纹（一个原本没上过播客的人，现在有语料了）。

而且这不是空想——**斯坦福那篇论文正是这么做的**：1052 个人的 2 小时访谈，是由一个 **AI 访谈者**按标准化协议 + 动态追问完成的，因为「1000 场访谈超出单个研究生的时间」。他们证明了 AI 访谈者能采出足够复现本人行为的信息量。我们比他们多一样东西：**我们的 AI 访谈者不是通用协议，是某个真实优秀主持人的蒸馏。**

### 3.2 访谈者 = 三个组件，不是一个 prompt

把主持人指纹直接塞进 system prompt 会得到一个"语气像但不会问"的东西。真正的访谈者需要：

| 组件 | 职责 | 来自指纹的哪一部分 |
|---|---|---|
| **弧线规划器** | 一场访谈的议题顺序与时间预算 | 话题弧线 |
| **追问引擎** | 判断当前回答是否"过关"，不过关就追 | 追问触发器 + 追问深度 |
| **风格层** | 措辞、过渡、语气 | 开场模式 / 过渡话术 |

**追问引擎是核心，也是最容易做砸的地方。** 它需要一个明确的「回答质量判据」：

```
回答被判为"需要追问"，当且仅当满足任一：
  · 含模糊量词而无具体数字（"很多"/"不少"/"挺快"）
  · 给了结论但没给依据
  · 与该受访者此前语料中的表述冲突   ← 这里用到了受访者的指纹
  · 回避了问题的核心（答非所问检测）
  · 出现了值得展开的新实体/概念
追问链长度上限 = 该主持人指纹的 P75 追问深度（不是无限追）
```

第 3 条是这套系统独有的能力：**AI 主持人能问出「你 2021 年说过 X，现在为什么改了」**——因为它手上有受访者的双时态命题库（§6.3）。人类主持人做不到这个，除非他事先做了几十小时功课。**这是产品真正的差异化，不是"AI 能对话"这种人人都有的东西。**

### 3.3 产品形态

| 形态 | 说明 | 优先级 |
|---|---|---|
| **AI 采访我** | 用户选一个主持人指纹，被访 30–60 分钟，产出一集可读文稿 | P0，最小可验证 |
| **预演** | 真人主持人在录制前，先让 AI 版嘉宾陪练，看哪些问题会被挡回来 | P1，对创作者价值高 |
| **补问** | 已有一集里主持人漏问的，AI 事后补一轮 | P2 |

### 3.4 与嘉宾蒸馏的依赖关系

AI 主持人**依赖**受访者指纹才能发挥全部能力（追问引擎的第 3 条）。所以路线上它排在嘉宾蒸馏之后，但**基础版（弧线 + 风格 + 前两条追问触发器）不依赖**，可以早做。

### 3.5 必须标注

生成的节目、AI 主持人的每一句话，都要**显式标明是 AI**。这一条我按产品质量要求保留，与法律无关——用户如果分不清对面是不是真人，这个产品的信任基础就没了。技术上沿用 §10 的双标识方案。

## 4. 社区方案参考与选型

| 方案 | 解决的问题 | 我们采纳什么 | 我们不采纳什么 |
|---|---|---|---|
| **Stanford《Generative Agent Simulations of 1,000 People》**（arXiv 2411.10109）1052 人 × 2h 访谈 → 复现本人问卷回答，准确率 85%；5 个社科实验复现 4 个 | 「长访谈能否表征一个人」 | ①**方法论直接可移植**：播客就是 2h 访谈 ②**留出集预测**作为北极星指标 ③他们的 agent 输入是**访谈全文 + 结构化记忆**，不是微调 | 不做行为模拟 agent。我们做**档案**，不做**替身** |
| **Zep / Graphiti 双时态知识图谱**（arXiv 2501.13956，Graphiti 20k+ star） | 事实会过期，且不能删 | **双时态模型**：`valid time`（世界上何时为真）+ `ingestion time`（系统何时知道）；冲突时**失效而非删除** | 不整体替换我们的 Postgres+pgvector 栈；只借模型 |
| **pyannote / WeSpeaker ResNet34（256 维）/ NeMo TitaNet** | 跨录音说话人识别 | 声纹 embedding + 跨集凝聚聚类，作为身份解析的**强信号之一** | 不单独依赖声纹（见 §6.1 失败模式） |
| **HippoRAG2 / GraphRAG / LightRAG** | 实体中心检索 | **实体优先检索**（先命中人，再取其发言 chunk）；HippoRAG2 在多跳问答上最优 | 不用 GraphRAG 的 global community summary —— 评测显示它在细节问答上丢证据 |
| **Argument Mining LLM 综述**（arXiv 2506.16383） | claim / evidence / stance / relation 抽取 | 用 prompt 驱动的联合抽取替代旧的多分类器流水线 | —— |
| **Delphi.ai**（Sequoia 领投 $16M A 轮） | 已验证的商业形态 | ①**只用本人内容训练** ②**仅限已验证本人创建** ③数据不汇入通用模型 | **我们的处境根本不同**：Delphi 是本人授权的自建克隆，我们是第三方公开对谈的衍生分析。不能照抄它的产品形态（§10） |

### 4.1 一个必须点破的差异

Delphi / Character.AI 是**本人同意的自我克隆**。我们做的是**从第三方公开发言中析出的人物档案**。

这不是程度差别，是性质差别。它决定了：**主产品不能是「和某某聊天」，只能是「某某说过什么、怎么变的、凭什么」**。交互问答是受控的次级功能，不是主线。

## 5. 系统架构

```
                        ┌──────────────────────────────┐
   已有 ASR/转写 ──────► │  L0  身份解析 Identity        │ ← 新建，核心
                        │  声纹 ⊕ 元数据 ⊕ 文本自指     │
                        └──────────────┬───────────────┘
                                       │ SpeakerIdentity
                        ┌──────────────▼───────────────┐
                        │  L1  归属语料 Utterance       │ ← 接线即可
                        │  Turn ─participantId→ Entity  │
                        └──────────────┬───────────────┘
                                       │
                        ┌──────────────▼───────────────┐
                        │  L2  命题层 Proposition       │ ← 扩展 ThoughtUnit
                        │  断言 + 立场 + 对冲 + 证据类型 │
                        │  双时态：assertedAt/supersededAt│
                        └──────────────┬───────────────┘
                                       │
                        ┌──────────────▼───────────────┐
                        │  L3  指纹层 Fingerprint       │ ← 新建
                        │  跨集聚合 + 漂移检测 + 谱系    │
                        └──────────────┬───────────────┘
                                       │
                        ┌──────────────▼───────────────┐
                        │  检索/呈现  实体优先 RAG       │
                        └──────────────────────────────┘
```

### 5.1 复利飞轮（你说的 infra 就是这个）

```
新一集 ──► 身份解析 ──► 声纹库 +1、别名表 +1、共现网络加密
   ▲                              │
   └──── 下一集解析更准 ◄──────────┘
```

具体机制，不是空话：
- 每解析成功一个人，其 `SpeakerVoiceprint` 入库 → 下次跨集匹配多一个锚点
- 每确认一个别名（「柯丽一鸣」=「Kellie」=「一鸣」）→ `Entity.aliasesJson` 增长 → L1 exact 命中率上升，省掉 LLM 仲裁
- 共现网络变密 → 可用「这一集另外三人都认识 X」做**关系先验**，消歧同名人

**冷启动的量级估算**：3 小时中文播客 ≈ 3 万字转写。一个高产嘉宾 20 次出场 ≈ 60 万字，完全在单次上下文处理能力之内。1000 人 × 20 集 = 2 万集，按当前抽取成本约 ¥0.3/集 ≈ ¥6000 全量重建一次。**这个量级是可负担的，可以放心设计成「可重跑」而不是「一次性」。**

## 6. 关键算法设计

### 6.1 身份解析（L0）—— 三信号融合

**不要只用声纹。** 声纹的失败模式很具体：

- 同一人换麦克风 / 不同平台转码 → embedding 漂移
- 跨年份（声音会变）
- 远场 / 电话连线嘉宾
- 中文播客大量存在的「同一集里多人重叠说话」

**三路信号**：

| 信号 | 来源 | 精度 | 召回 | 成本 |
|---|---|---|---|---|
| **声纹** | WeSpeaker/pyannote embedding，段级均值 | 中高 | 高 | 需过一遍音频 |
| **元数据** | RSS `<itunes:author>`、标题「对谈X」、show notes | **很高** | 低（常缺失） | 几乎为零 |
| **文本自指** | 「我是X」/ 主持人「欢迎X」/「我在Y公司」 | 高 | 中 | 一次 LLM |

**融合策略**（分数级融合 + 显式不确定带）：

```
score = w_v · cos(voiceprint) + w_m · meta_match + w_t · text_match

score ≥ 0.85            → 自动关联
0.60 ≤ score < 0.85     → 进人工确认队列   ← 这一带是产品质量的关键
score < 0.60            → 新建 Entity
```

中间带**必须存在且必须有 UI**。实体消歧文献（Splink / Zingg 这一路）的共识就是：高精度阻塞 + 成对打分 + 聚类 + **不确定带人工复核**。没有这一环的系统一定会脏。

**错误合并是最贵的错误**——它会毒化整个人物档案，且难以察觉。因此：

- `SpeakerIdentity` 是**关联表**，不是把 `entityId` 塞进 `Participant`
- 合并/拆分是一等操作，带审计轨迹
- 永不破坏性合并：拆开只需删关联行

```prisma
/// L0：一集里的说话人 ↔ 跨集真实人物。关联表而非外键，
/// 因为错误合并必须能无损回滚。
model SpeakerIdentity {
  id            String   @id @default(cuid())
  participantId String   @unique
  participant   Participant @relation(fields: [participantId], references: [id], onDelete: Cascade)
  entityId      String
  entity        Entity   @relation(fields: [entityId], references: [id], onDelete: Cascade)
  confidence    Float
  method        String   // voiceprint | metadata | text | fused | manual
  evidenceJson  Json     // { voiceCos, metaHit, textQuote, reviewerId }
  reviewedBy    String?  // 人工确认者
  reviewedAt    DateTime?
  createdAt     DateTime @default(now())

  @@index([entityId])
  @@index([confidence])
}
```

### 6.2 命题抽取（L2）

现有 `ThoughtUnit` 有 `type` 和 `stance`，需要补三个字段才够支撑「变化检测」：

```prisma
model ThoughtUnit {
  // ...现有字段
  modality    String?  // asserted | hedged | hypothetical | quoted | joking
  evidenceType String? // experience | data | authority | analogy | none
  polarity    Float?   // -1..1，对命题的支持度
}
```

**`modality` 是防止诽谤的关键字段。** 「我觉得可能 AGI 五年内到」和「AGI 五年内一定到」，以及**引用别人的话**「有人说 AGI 五年内到」，在朴素抽取里会被压成同一条命题。一旦压平，「他改口了」的判断就会是错的。

### 6.3 变化检测 —— 最危险的功能，单独设计

**朴素做法（会出事）**：找到 2021 年的命题 P 和 2024 年的 ¬P，输出「他改变了立场」。

**为什么会出事**：矛盾 ≠ 观念改变。可能是
- 语境不同（在讨论不同对象）
- 假设性陈述（「如果……那我会说」）
- 引用他人观点
- 反讽
- 转写错误 / 归属错误（L0 错了这里就全错）

**设计**：

1. 只在 `modality = asserted` 的命题之间比较
2. 要求两侧都有 `EvidenceSpan`（可跳回原音频）
3. 命题需先归一到同一 `CanonicalClaim`，且要求主题语境相似度阈值
4. **系统不下断言**。UI 呈现是：

   > **同一议题，不同时间**
   > 2021-03 ——「……」 ▶ 听原声
   > 2024-08 ——「……」 ▶ 听原声

   而不是「他改变了看法」。让读者自己判断。这既更准确，也是唯一安全的呈现方式。
5. 置信度低于阈值不展示，宁可漏报

**双时态模型**（借 Zep/Graphiti）：

```prisma
model PersonClaim {
  id           String   @id @default(cuid())
  entityId     String                    // 谁说的
  canonicalId  String?                   // 归并到哪个 CanonicalClaim
  text         String
  modality     String
  polarity     Float

  assertedAt   DateTime                  // valid time：他何时说的（用单集发布日）
  ingestedAt   DateTime @default(now())  // system time：我们何时知道的
  supersededById String?                 // 被哪条后续陈述取代
  supersededAt   DateTime?               // 失效而非删除

  thoughtUnitId String                   // 溯源
  @@index([entityId, assertedAt])
  @@index([canonicalId])
}
```

「失效而非删除」很重要：2021 年那句话**当时是真的说了**，它永远不该从档案里消失，只是不再代表当下立场。

### 6.4 统一中文语义层：一个必须处理的副作用

> 来自你的第 2 条回复：所有播客最终在中文语义上分析，国外播客基于中文译文蒸馏。
> 这消掉了跨语言实体消歧的复杂度——但它会**破坏 L3 里最有价值的两个字段**。

**问题**：`类比词汇` 和 `口头禅` 是指纹里最个人化、几乎等同签名的部分。而翻译恰恰会把它们抹平：

| 原文 | 直译后 | 丢失了什么 |
|---|---|---|
| "it's turtles all the way down" | "一层套一层" | 这是个**有文化来源的特定典故**，说话人选它而非别的，本身是信号 |
| "we're skating to where the puck is going" | "我们要提前布局" | 冰球隐喻 → 变成商业套话，个人色彩归零 |
| 反复说的 "look," / "right?" | 通常被翻译丢弃 | 口头禅整体消失 |

翻译模型会把不同人的比喻**收敛到同一套中文商业词汇**。结果：所有英文播客嘉宾的「类比词汇」字段会长得一模一样——**那是翻译模型的签名，不是他们的**。

**设计对策：语义走译文，风格走原文。**

```
命题层 L2（他主张什么）      ← 用中文译文    ✓ 语义在翻译中基本保真
指纹层 L3 语义类字段          ← 用中文译文    ✓ 核心主张/立场光谱/引用谱系
指纹层 L3 风格类字段          ← 必须用原文    ✗ 类比词汇/口头禅/对冲率/句式
```

落地要求：`Turn` 已有 `translationJson`，**原文必须保留而非被替换**（当前 reader 已是这样，别在蒸馏管线里丢掉）。风格特征抽取读 `turn.text`（原文），语义抽取读译文。

**对冲率也受影响**：英文的 "I think maybe" / "sort of" / "I'd argue" 有细腻的确信度梯度，中译常统一成「我觉得」。所以 `modality` 判定同样应在原文上做。

**给纯中文播客的好消息**：以上全部不适用，中文语料原文=分析文本，风格信号完整。**优先用中文播客验证 L3，英文的风格字段标记为「基于译文，仅供参考」或直接不展示。**

## 9. 评测体系

不做评测的蒸馏系统等于没做。四层各有指标：

| 层 | 指标 | 方法 | 目标 |
|---|---|---|---|
| **L0 身份** | 合并 precision / recall | 人工标注 200 对 participant，算 P/R | P ≥ 0.98（合并错代价极高，宁可漏） |
| **L1 归属** | 发言归属准确率 | 抽 500 段人工核对说话人 | ≥ 0.95 |
| **L2 命题** | 忠实度 | 人工评「这条命题是否忠实于原话」 | ≥ 0.90 |
| **L2 变化** | **误报率** | 系统标出的立场变化，人工核对真伪 | **≤ 0.05（最危险的指标）** |
| **L3 指纹** | **留出集预测准确率** | 见下 | 北极星 |

### 9.1 北极星：留出集预测

直接移植斯坦福 genagents 的方法论：

1. 取某人的 N 集，留出**最新一集**
2. 用前 N−1 集蒸馏出指纹
3. 从留出集里抽出该集讨论的 K 个议题
4. 让指纹**预测**他在这些议题上的立场
5. 与留出集真实发言比对

这是可跑、可证伪、可持续追踪的。斯坦福在 2h 访谈上做到 85% 行为复现；我们有同一人的多次长对谈，理论上限更高——**如果 L0/L1 是对的**。

**这个指标同时是 L0 的照妖镜**：身份解析错了，预测准确率会立刻塌，比任何单独的归属指标都灵敏。

| 2 | 跨语言同一人 | 不存在——全部统一到中文语义层分析 | §6.4（并指出翻译对风格字段的副作用与对策） |
| 3 | T0 引用边界 | 单条 ≤200 字 + 必带原链接，不走法务 | §10.2 表格；§10 整节挂起 |
| 4 | 认领 | 不做 | §8.1 移除入口；§10.2 门槛退回覆盖度 |

### 新的未决问题（由上面四条决定引出）

1. **AI 主持人生成的内容，要不要回灌语料库？** 回灌能让飞轮转得更快，但也会让指纹逐渐
   拟合自己的输出（模型坍缩）。**建议：受访者的真人发言回灌，AI 主持人的话不回灌。**
2. **主持人指纹用谁的？** 用户自选任意主持人？还是只能用平台签约/授权的？这决定产品是
   「主持人风格市场」还是「单一自有访谈者」——商业模式差别很大。
3. **一集里主持人和嘉宾角色如何自动判定？** RSS 的 `<itunes:author>` 只给节目主，多主持
   或嘉宾主持互换时会错。是否需要用「谁问问题多」这类结构特征兜底？
4. **英文播客的风格字段展示策略**：标注「基于译文」还是直接隐藏？前者诚实但削弱产品观感。
