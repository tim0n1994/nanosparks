## Problem Statement

Solo founders and small team operators need to understand their business metrics (MRR, churn, LTV, revenue trends) but spend 80% of their time cleaning and preparing Stripe data before they can analyze it. They currently export CSVs, wrangle them in Excel or Python scripts, and manually build dashboards in Notion or Google Sheets. This is tedious, error-prone, and delays decision-making.

## Demand Evidence

- Founder (JC) experiences this pain directly: uses multiple fragmented tools for data analysis and visualization
- The 80/20 split (80% cleaning, 20% analyzing) was observed in actual workflow behavior
- Status quo involves manual CSV exports + Excel/Python + BI tools — a clear workaround indicating real pain

## Status Quo

Current workflow for a solo founder checking monthly metrics:
1. Export Stripe data as CSV
2. Open in Excel or Python notebook
3. Clean data (handle refunds, duplicates, currency conversions, subscription status changes)
4. Calculate metrics manually or with formulas
5. Copy results into Notion/Google Sheets for sharing
6. Repeat monthly

This takes 2-4 hours per month and is error-prone. Most founders skip it until they "have time," which means they're flying blind on key business metrics.

## Target User & Narrowest Wedge

**Target user:** Solo founder or small team operator (2-10 people) who uses Stripe for payments and needs to report metrics to investors, teammates, or themselves. They don't have a data team and can't justify a $500+/month BI tool.

**Narrowest wedge:** Stripe-only data connector that automatically cleans raw Stripe data and produces a single-page dashboard with key SaaS metrics. Shareable via link. Zero configuration beyond OAuth connection.

## Constraints

- Must work without code (target user is not technical)
- Must handle Stripe's data complexity (refunds, prorations, multi-currency, subscription changes)
- Must produce accurate metrics (founders make decisions with these numbers)
- Must be shareable (investor updates, team standups)
- Must be fast (data sync in seconds, not minutes)
- Must be secure (financial data — encryption at rest, Stripe OAuth, no data retention beyond user request)

## Premises

1. **The real pain is data preparation, not insight generation.** Users will pay to eliminate tedious cleaning work before they'll pay for smarter alerts. — AGREED
2. **The target user is a solo founder or small team operator who needs data insights without hiring a data person.** — AGREED
3. **The smallest wedge is automating data ingestion + cleaning for ONE common data source (Stripe), producing a clean dashboard they can share with investors or teammates.** — AGREED

## Approaches Considered

### Approach A: The Connector (RECOMMENDED)
A simple web app that connects to Stripe, automatically cleans raw data, and produces a single-page dashboard with key metrics. Shareable via link. No code required.

- **Effort:** Small (3-4 weeks for a solo builder)
- **Risk:** Low
- **Pros:** Ships fast, solves a real pain for a specific user, easy to explain
- **Cons:** Limited to Stripe, doesn't scale to other sources, feature-poor vs full BI

### Approach B: The Pipeline
A general-purpose data pipeline builder. Users connect any source, define cleaning rules via a visual interface, and route clean data to any destination.

- **Effort:** Large (2-3 months)
- **Risk:** High
- **Pros:** Scales to many use cases, defensible moat, platform play
- **Cons:** Complex to build, hard to get right, many competitors in adjacent spaces

### Approach C: The AI Analyst
A chat-based interface where founders upload a CSV or connect an account, and an AI agent cleans data and generates insights.

- **Effort:** Medium (3-4 weeks)
- **Risk:** Medium
- **Pros:** Novel UX, leverages AI, high "whoa" factor
- **Cons:** AI reliability for financial data is spotty, harder to debug when wrong

## Recommended Approach

**Approach A: The Connector**

Rationale: Validates demand with a specific user and source before building the platform. Stripe is the most common payment processor for SaaS founders. The metrics (MRR, ARR, churn, LTV) are well-understood and calculable from Stripe's API. Once 10+ paying users validate the model, expand to other sources (Google Analytics, Shopify, etc.).

## Open Questions

1. Which Stripe metrics are most important for v1? (MRR, churn, LTV, ARPU, expansion revenue?)
2. How frequently should data sync? (Real-time, daily, on-demand?)
3. What's the pricing model? (Free tier with limited history, paid for unlimited?)
4. Should the dashboard be embeddable in Notion/Slack?
5. Dashboard layout: single-page with metric cards + trend charts, or tabbed by category?
6. Multi-currency: auto-detect from Stripe or user-configurable base currency?
7. MRR accuracy target: "within 1% of Stripe's internal reporting" — define test cases for edge cases (prorations, trials, discounts)

- [ ] First dashboard loads in < 10 seconds after connection
- [ ] MRR calculation matches Stripe's internal reporting within 1%

## Distribution Plan

- **Channel:** Product Hunt launch, Indie Hackers post, Twitter/X founder community
- **Pricing:** Free for single user + 90 days history; $19/mo for unlimited history + team sharing
- **CI/CD:** GitHub Actions for automated testing and deployment to Vercel/Railway

## Dependencies

- Stripe OAuth integration (Stripe Connect)
- Stripe API endpoints: `customers`, `subscriptions`, `charges`, `invoices`, `refunds`
- Frontend framework (Next.js recommended)
- Database for caching cleaned data (PostgreSQL or SQLite for MVP)
- Hosting platform (Vercel for frontend, Railway/Render for backend)
- Error handling: Stripe API rate limits, malformed data, OAuth token expiry
